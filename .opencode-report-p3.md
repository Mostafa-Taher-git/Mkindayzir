## TRUE BUGS

### BUG-1 — `response_met` is computed against the first-response time itself, so it is always 1
**Severity:** High (SLA correctness / reported data is meaningless)
**File:** `app/routes_sla.py:90-92`
**Evidence:** The response SLA deadline is built from the *first response time* rather than the ticket creation time:
```python
resp_target = helpers._parse_iso(row["first_response_at"]) + timedelta(hours=policy["response_hours"])
response_met = 1 if helpers._parse_iso(row["first_response_at"]) <= resp_target else 0
```
`first_response_at <= first_response_at + N hours` is always true, so `response_met` is always 1 whenever a first response exists and a policy is linked. **Live proof:** ticket 27 (Standard policy, 8h response SLA) had its `first_response_at` set ~50h after creation (clearly missed), then resolved → API returned `response_met = 1`. Correct semantics: target = `created_at + response_hours` (needs a JOIN to `tickets.created_at`).
**Recommended fix:**
```python
created = helpers._parse_iso(conn.execute(
    "SELECT created_at FROM tickets WHERE id=?", (ticket_id,)).fetchone()["created_at"])
resp_target = created + timedelta(hours=policy["response_hours"])
response_met = 1 if helpers._parse_iso(row["first_response_at"]) <= resp_target else 0
```
Also add a guard: if `_parse_iso(first_response_at)` returns `None`, `None + timedelta` raises `TypeError` → 500 during resolve.

### BUG-2 — Live breach status never computed for open tickets; overdue tickets show "On track"
**Severity:** High (core SLA feature — at-risk/breached badges never appear while a ticket is open)
**Files:** `app/routes_sla.py:44-63` (stores `breach_at`), `app/routes_tickets.py:617-633` (`_sla_summary`), `static/js/app.js:43-46` (badge logic)
**Evidence:** `ticket_sla.breached` is only ever set inside `evaluate_on_resolve` (routes_sla.py:86), which runs only on the resolve transition (routes_tickets.py:269-270). The read path (`_sla_summary`, the `/sla` endpoint) just returns the stored flag; it never compares `breach_at` against "now". **Live proof:** backdated `breach_at` on open ticket 25 to 2026-08-16 (past) → `GET /api/tickets/25/sla` still returned `breached = 0`, `resolution_met = null`; the SPA therefore renders a green "On track" badge for a ticket that is already 1 day past its SLA deadline. `test_recently_created_ticket_not_breached` only covers fresh tickets and misses this.
**Recommended fix:** compute breach live on read (e.g. in `_sla_summary`/`ticket_sla`), or run a periodic sweep that marks overdue rows:
```python
"breached": bool(row["breached"]) or (now() > _parse_iso(row["breach_at"]))
```
and use `resolution_met`/`breach_at` in the badge for "at risk" (open, within window → on-track; past `breach_at` → breached).

### BUG-3 — First response is not recorded when an agent comments (only on assign)
**Severity:** Medium (understates response performance; contradicts phase-3 brief "record first response on assign/add_comment")
**File:** `app/routes_tickets.py:315-350` (`add_comment` never calls `sla.record_first_response`); the only call site is routes_tickets.py:189 in `assign`.
**Evidence:** Live: agent added a public comment to ticket 28 *without assigning* → `first_response_at` stayed `NULL`. An agent's first human touch via comment is the most common first response and is currently ignored.
**Recommended fix:** in `add_comment`, after inserting, when `is_agent_or_manager(user) and t["requester_id"] != user["id"]`, call `sla.record_first_response(tid)`.

### BUG-4 — `POST /api/tickets` with an invalid `category_id` returns HTTP 500 (unhandled IntegrityError)
**Severity:** Medium (robustness; 500 instead of 400; leaks a Werkzeug debugger page in dev)
**File:** `app/routes_tickets.py:98,128-137`
**Evidence:** Live: `category_id=9999` → `sqlite3.IntegrityError: FOREIGN KEY constraint failed` → HTTP 500. Because `run.py:17` sets `debug=True`, the response is a full Werkzeug debugger HTML page (source/traceback leak, interactive console). Pre-existing, but it sits directly on the Phase-3 routing path (`categories.default_team_id` lookup at routes_tickets.py:113-117).
**Recommended fix:** validate that `category_id` exists (and is active) before the INSERT and return `400`:
```python
if category_id:
    cat = db.get_db().execute("SELECT id FROM categories WHERE id=?", (category_id,)).fetchone()
    if not cat:
        return jsonify(error="Unknown category"), 400
```

## Nits (non-blocking)

1. **Direct `new/assigned → closed` skips SLA evaluation.** `evaluate_on_resolve` only fires when `final_status == STATUS_RESOLVED` (routes_tickets.py:269). Lifecycle allows `new→closed` and `assigned→closed` (lifecycle.py:23,28), so such tickets keep `resolution_met=NULL`/`breached=0` forever. Consider evaluating on close too, or block close-without-resolve for open tickets.
2. **Requester can override category routing.** The create form exposes a Team dropdown to every role (app.js:876-878) and `create_ticket` honors a client-supplied `team_id` (routes_tickets.py:100,113-117). A requester can route a Hardware ticket to Finance, defeating `categories.default_team_id`. If routing is meant to be authoritative, ignore/hide `team_id` for requesters (live: sam routed Hardware→Finance team successfully).
3. **N+1 queries.** `_serialize` (routes_tickets.py:595-615) calls `_sla_summary` per row → one extra SELECT per ticket in every list call. Fine at small scale; a `LEFT JOIN ticket_sla` in the list query would remove it.
4. **Private cross-module import.** `attach_sla`/`evaluate_on_resolve` use `helpers._parse_iso` (routes_sla.py:53,85,91) — make `parse_iso` public or move to `db`.
5. **Wording:** a *resolved* ticket that missed its target renders "SLA at risk" (app.js:44 and :706); "SLA missed/breached" is clearer. Badge title also uses an odd `" . due "` separator (app.js:46).
6. **`response_met` stays `NULL` when never responded.** If a ticket resolves without any first response, `response_met` is left `NULL` (routes_sla.py:89); consider `0` (missed) so reports count it.
7. **`pick_policy` tie-breaking is insertion-order.** With multiple priority-only policies the first row wins (routes_sla.py:35-41); prefer an explicit `ORDER BY` (e.g. most-specific/longest) for determinism.
8. **Hard-coded 72h fallback** when no policy matches (routes_sla.py:57) duplicates the "Standard" policy; reference it instead.
