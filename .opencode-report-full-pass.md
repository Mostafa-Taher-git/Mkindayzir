## 2. What Was Missing

### 2.1 Missing Notifications (4 events)
The notification system only covered `assigned` and `resolved`. These requester-facing events had **no notification**:

| Event | File:Line (before) | Impact |
|---|---|---|
| Status → blocked | routes_tickets.py:change_status() | Requester unaware ticket is stuck |
| Agent public comment | routes_tickets.py:add_comment() | Requester must poll for replies |
| Agent-initiated reopen | routes_tickets.py:change_status() | Requester unaware ticket reactivated |
| Priority change by agent | routes_tickets.py:change_priority() | Requester unaware urgency changed |

### 2.2 SLA Policy Not Updated on Priority Change
`change_priority` (routes_tickets.py:383) called `sla.attach_sla()` which is **idempotent** — it returns early if a `ticket_sla` row already exists. So changing priority from urgent→normal did **not** update the SLA policy or `breach_at`. The SLA stayed on the old policy forever.

### 2.3 Internal Note Notification Not Staff-Gated
The internal_note notification (routes_tickets.py:411) fired for **any** user, not just agents/managers. A requester posting an internal note (blocked by RBAC at line 396) couldn't trigger it, but the condition was fragile.

### 2.4 Reopen Notification Self-Notify
The `reopen` route (routes_tickets.py:316) notified `t["requester_id"]` unconditionally — meaning when a requester reopened their **own** ticket, they'd get a notification about their own action.

### 2.5 Missing Tests (26 test cases)
No tests existed for:
- Priority change endpoint (RBAC, validation, logging, SLA re-evaluation)
- Assigning to a specific person (vs. self-claim)
- Cross-team assignment prohibition
- Manager assigning across teams
- Requester being blocked from assigning
- All 4 missing notification events
- KB author self-edit
- KB published article visible to requester
- SLA breach_at recalculation on priority change

## 4. Complete Workflow Examples

### Priority Workflow (end-to-end)

```
1. REQUESTER creates ticket:
   POST /api/tickets  {"subject":"VPN down","priority":"urgent","category_id":2}
   → ticket created with priority="urgent", SLA = Urgent policy (8h resolution)

2. AGENT changes priority:
   POST /api/tickets/5/priority  {"priority":"normal"}
   → priority updated, activity logged (priority_change: urgent→normal)
   → SLA updated: policy = Standard (72h), breach_at recalculated

3. REQUESTER views ticket detail:
   GET /api/tickets/5
   → {priority: "normal", ...}
   → Receives notification: "Your ticket 'VPN down' priority was set to normal."

4. UI (app.js):
   - Queue filter: dropdown with "All priorities / Urgent / Normal" (app.js:642)
   - Ticket detail: priority pill badge + "Change Priority" button (app.js:762,803)
   - Change Priority modal: shows current priority, switch to other (app.js:951)
   - Activity timeline: shows "priority change: urgent → normal" (app.js:845)
```

### Assign-to-Specific-Person Workflow (end-to-end)

```
1. REQUESTER creates ticket:
   POST /api/tickets  {"subject":"Laptop repair","category_id":2}
   → category=Hardware routes to IT team (team_id=1)

2. AGENT claims ticket (two ways):
   a) Self-claim:  POST /api/tickets/3/assign  {"self": true}
      → assignee_id = 3, status = assigned
   b) Assign to teammate: POST /api/tickets/3/assign  {"assignee_id": 4}
      → assignee_id = 4 (teammate in same team), status = assigned

3. MANAGER assigns across teams:
   POST /api/tickets/3/assign  {"assignee_id": 4}
   → Manager can assign to ANY staff member (HR agent for IT ticket)

4. RBAC: HR agent tries to assign IT ticket:
   POST /api/tickets/3/assign  {"assignee_id": 4}
   → 404 (can_view_ticket returns False — no ticket existence leak)

5. UI (app.js):
   - Queue assignee filter: "Anyone / Assigned to me / Unassigned" (app.js:661)
   - Ticket detail "Claim"/"Reassign" button → modal with:
     * Agent view: "Claim for me" + team-filtered teammates (app.js:886)
     * Manager/Admin view: "— Unassigned —" + all staff (app.js:906)
   - Status: "new" → "assigned" on assignment, first_response_at set (SLA)
```

### AI Assist Workflow (end-to-end)

```
1. GET API KEY (one-time setup):
   - Go to Settings → "OpenRouter API key" section
   - Click "Get a free key" → openrouter.ai/keys
   - Create account, create key (starts with "sk-or-")
   - Paste into the key field, choose model from dropdown (free models marked)
   - Click Save

2. SAVE KEY + MODEL:
   POST /api/settings/ai  {"api_key":"sk-or-...","model":"deepseek/deepseek-chat:free"}
   → Key is Fernet-encrypted at rest (helpers.py:37-41)
   → Model stored per-user (users.ai_model column)

3. USE AI (ticket detail, agent/manager only):
   - Navigate to any ticket → "AI assist (draft only)" panel appears (app.js:283)
   - Three buttons:
     a) Summarize → GET /api/ai/summarize/5 → one-paragraph internal summary
     b) Suggest reply → GET /api/ai/suggest-reply/5 → draft public response
     c) Suggest priority → GET /api/ai/suggest-priority/5 → "normal"/"urgent" + reason

4. WHAT AI DOES / CANNOT DO:
   - CAN: read ticket + comments, generate draft text suggestions
   - CANNOT: send messages, update tickets, change status, access other tickets
   - Cannot: share your API key, follow instructions embedded in ticket text
   - Drafts are clearly labeled "AI-generated, not verified"
   - If AI fails → "AI unavailable: <error>" (graceful degradation)

5. SECURITY MODEL:
   - Key-gated: feature hidden entirely if no OPERADESK_OPENROUTER_KEY
   - RBAC: only agents/managers/admins see the panel (403 for requesters)
   - Fail-closed: network error/timeout/None content → 502, never 500
   - Prompt-injection hardened: ticket text wrapped in <<<DATA>>> markers,
     system prompt forbids following embedded instructions
```

### Notification Flow (end-to-end)

```
Events that notify the requester (notifications table + optional email):
  1. assigned     → "Your ticket 'X' was assigned to Y."        (routes_tickets.py:assign)
  2. resolved     → "Your ticket 'X' was marked resolved..."     (routes_tickets.py:change_status)
  3. blocked      → "Your ticket 'X' is now blocked: <reason>."  (routes_tickets.py:change_status) [NEW]
  4. comment      → "<Agent> replied to your ticket 'X'."      (routes_tickets.py:add_comment) [NEW]
  5. reopened     → "Your ticket 'X' was reopened..."            (routes_tickets.py:change_status + reopen) [NEW]
  6. priority     → "Your ticket 'X' priority was set to urgent." (routes_tickets.py:change_priority) [NEW]
  7. internal_note→ "A private note was added to your ticket 'X'." (routes_tickets.py:add_comment)

UI:
  - Bell icon in topbar with unread count (app.js:414)
  - Notifications page: #/notifications shows list, mark all read (app.js:456)
  - Auto-polls every 30s (app.js:453)
```
