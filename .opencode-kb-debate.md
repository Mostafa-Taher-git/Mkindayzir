# OpsDesk Knowledge Center — Revised Plan

## Critique Summary

The original 5-increment plan is **sound in vision but wrong in sequencing and scope**. Here are the core problems:

### 1. Wrong starting point: hierarchy before links
K1 leads with `parent_id` and a tree sidebar. That forces a folder-style navigation decision before anyone knows how articles actually relate. Odoo Knowledge uses workspaces; Frappe uses categories; the current code already has `category_id`. Adding `parent_id` creates a second hierarchy axis that will conflict with categories and invites circular-reference bugs. **Links come first because they require the smallest schema change, deliver immediate value, and inform whether hierarchy is even needed.**

### 2. K3 conflates two unrelated features
"Collections + Ticket Integration" bundles a lightweight grouping feature with the single highest-value ticket-KB bridge. Splitting them lets ticket integration ship faster and be tested independently. Ticket integration also reuses existing ticket patterns; collections do not.

### 4. K4 over-reaches
A live graph view rendered client-side in vanilla JS is frontend-heavy and hard to make performant in SQLite. Analytics is a backend query problem. Merging them means either shipping a slow graph or a half-baked analytics panel. **Analytics should ship alone; the graph should defer to v2.**

### 5. K5 is a grab-bag
Versioning + properties + AI assists are three different bets. Versioning needs storage discipline and UI chrome. AI assists need a working AI provider. Bundling them together means any one blocker stalls the whole increment. **Split them into two separate increments.**

### 6. Existing infrastructure is under-used
The plan reinvents:
- **AI layer**: `app/ai/client.py` already exists with OpenRouter, prompt-injection hardening, and `suggest_reply` / `summarize_ticket` helpers.
- **Reports layer**: `app/routes_reports.py` already has manager-only analytics patterns, CSV export, and date-range queries.
- **Ticket patterns**: `log_activity()`, `is_agent_or_manager()`, `can_view_ticket()`, RBAC scoping, and attachment storage are all reusable for KB metadata and ticket-KB links.

The revised plan reuses these instead of rebuilding them.

## Ranked Risks

| Rank | Risk | Mitigation |
|------|------|------------|
| **R1** | **Graph performance at scale** — `/api/kb/graph` traversing links + collections + ticket links in a single SQLite query will degrade past ~1,000 articles. | Defer graph to v2. Ship analytics first; add a simple "related articles" link list instead. |
| **R2** | **AI dependency** — AI assists in K5 require `OPERADESK_OPENROUTER_KEY`. If it's unset, the feature must degrade gracefully. | The existing `ai_enabled()` + fail-closed `_complete()` already do this. Reuse them; surface "AI unavailable" in the UI. |
| **R3** | **Schema migration in SQLite** — Adding `parent_id`, `kb_article_links`, `kb_collections`, `ticket_kb_links`, `kb_article_versions` requires multiple `CREATE TABLE` migrations. SQLite has limited `ALTER TABLE` support. | Add a lightweight migration runner in `app/lifecycle.py` or a one-time `migrate_kb.py`. Keep migrations idempotent. |
| **R4** | **Search UX regression** — Replacing `LIKE` with anything more structured must not break the existing `?q=` parameter or requester-only-published behavior. | Extend the existing query parameter set; keep `q` as a backward-compatible alias. Write a thin search adapter. |
| **R5** | **Frontend surface area** — Tree sidebar, drag/drop, backlinks panel, search facets, graph canvas, analytics charts, version history, collections tab = a lot of vanilla JS state. | Prioritize server-rendered HTML sections where possible. Keep the graph as a static pre-computed payload (defer to v2). |
| **R6** | **Circular hierarchy references** — `parent_id` allows A→B and B→A if not guarded. | Add a `CHECK` constraint or application-level cycle detection on `/api/kb/move`. |
| **R7** | **Duplicate AI detection** — Calling the LLM for every article pair is expensive and slow. | Defer duplicate detection to v2. Use simple title-similarity (Levenshtein or trigram) as a cheap heuristic if needed. |

## Revised Increment Order & Scope

### K1: Better Search + Filters *(was K2, moved to first)*
**Why first:** The current `LIKE` search is the most broken part of the KB. Fixing it has the highest user-facing ROI and lowest schema risk. It also establishes the filter pattern used by every later increment.

**Scope:**
- Extend `/api/kb` list with filters: `category_id`, `status`, `author_id`, `date_from`, `date_to`, `sort` (updated_at / views / helpful_pct).
- Add basic relevance ranking: exact title match > title contains > body contains.
- Frontend: filter bar on Help Center and Manage KB, active-filter chips, result count.
- **Do NOT add:** full-text search extensions (FTS5), semantic search (defer to v2).

**Reuses:** Ticket list filter pattern (`category_id`, `status`, `q`), `is_agent_or_manager()`, `login_required`.

---

### K2: Internal Links + Backlinks *(was K2, unchanged core)*
**Why second:** Links require only one new table (`kb_article_links`) and a small save-time parser. They create immediate cross-reference value and produce the edge data the eventual graph will need.

**Scope:**
- Schema: `kb_article_links (id, source_article_id, target_article_id, created_at, created_by_id)`.
- Backend: parse `[[Article Title]]` on save/create; resolve to `target_article_id` via title lookup (case-insensitive, best match). `/api/kb/<id>/links` CRUD. `/api/kb/<id>/backlinks` returns articles linking here.
- Frontend: inline link chip in article body, backlinks section below article, link autocomplete in editor.
- Guard against self-links and duplicate links.

**Reuses:** KB CRUD patterns, `_author_name()` helper style.

---

### K3: Ticket ↔ KB Integration *(extracted from K3, split)*
**Why third:** Agents resolving tickets is the #1 place KB value is proven. Linking articles to tickets turns the KB from a static brochure into a live workflow tool. This increment has the clearest success metric (tickets with linked articles resolve faster / need fewer follow-ups).

**Scope:**
- Schema: `ticket_kb_links (id, ticket_id, article_id, linked_by_id, linked_at, note)`.
- Backend: `/api/tickets/<id>/knowledge` lists linked articles. `/api/tickets/<id>/knowledge/suggested` returns top-5 article candidates by keyword overlap (title + body token match against ticket subject + description — no AI needed for v1).
- Frontend: "Attach article" panel in ticket detail, suggested-articles rail, remove-link action.
- **Do NOT add:** AI-generated suggestions (defer to K6).

**Reuses:** Ticket attachment pattern (magic-byte guard → manual link), `is_agent_or_manager()`, `helpers.log_activity()` for link events.

---

### K4: Collections *(extracted from K3, split)*
**Why fourth:** Collections are a lightweight grouping layer. They don't depend on hierarchy or ticket integration. They let managers build curated article sets (e.g., "Onboarding," "VPN Troubleshooting") without forcing a folder taxonomy.

**Scope:**
- Schema: `kb_collections (id, name, description, created_by_id, created_at)`, `kb_collection_articles (collection_id, article_id, position, added_at)`.
- Backend: collections CRUD, add/remove articles, reorder by `position`. `/api/kb/collections` list + detail.
- Frontend: "Collections" tab on article view, collection editor in Manage KB, collection widget on Help Center homepage.
- **Do NOT add:** collection sharing/permissions (reuse existing role checks; agents/managers see all collections).

**Reuses:** Category-like listing patterns, `is_agent_or_manager()`.

---

### K5: Knowledge Health Dashboard *(simplified from K4)*
**Why fifth:** Analytics has no UI dependencies on the graph. It uses the existing reports infrastructure and answers the manager question "is our KB healthy?" without requiring a visualization framework.

**Scope:**
- Backend: `/api/kb/analytics` returns:
  - Views (total, last 30 days)
  - Helpful % (from `kb_feedback`)
  - Orphan articles (0 views in last 90 days)
  - Stale articles (not updated in 90 days and not draft)
  - Top linked articles (from `kb_article_links` + `ticket_kb_links`)
  - Articles by category breakdown
- Frontend: "Knowledge Health" panel in Manage KB, simple bar/line charts using existing CSS (no chart library needed — use inline SVG or simple div bars).
- **Do NOT add:** graph view (defer to v2), heatmaps, per-agent KB contribution (nice-to-have).

**Reuses:** `routes_reports.py` patterns (manager-only gating, date math, aggregation queries).

---

### K6: Versioning + AI Assists *(split from K5)*
**Why last:** Versioning adds storage and UI complexity. AI assists depend on the OpenRouter key being configured. Both are valuable but neither is blocking. Shipping them together is fine because they share the same "AI/infrastructure" theme.

**Scope:**
- **Versioning:** `kb_article_versions (id, article_id, title, body, category_id, saved_by_id, saved_at, change_note)`. Snapshot on every publish or edit. `/api/kb/<id>/versions` list + diff. Frontend: version history dropdown, diff view.
- **AI assists:**
  - "Generate draft from ticket": reuse `app/ai/client.py` — call the existing `_complete()` with a KB-draft prompt wrapped in ticket data block.
  - "Suggest related articles": on article view, return top-3 articles by shared category + keyword overlap (cheap heuristic, no AI call).
  - **Do NOT add:** duplicate detection (defer to v2), auto-categorization.

**Reuses:** `app/ai/client.py` (OpenRouter, prompt-injection hardening, fail-closed `_complete()`), `helpers.log_activity()` for version-save events.

## What Defers to v2

| Feature | Reason |
|---------|--------|
| **Graph view** (Obsidian-style) | Frontend-heavy, SQLite traversal risk, low urgency. Analytics + backlinks give most of the value. |
| **Semantic / vector search** | Requires embeddings model, vector store, or external API. Adds dependency weight. |
| **Duplicate detection** | AI-dependent, per-article-pair cost, uncertain ROI. Use title-similarity heuristic in v1 if needed. |
| **Advanced permissions / workspace sharing** | Current RBAC (requester / agent / manager / admin) is sufficient for internal-only. |
| **Real-time collaboration** | Not needed for internal KB. Conflicts with versioning if both are half-baked. |
| **Rich block editor with slash commands** | Markdown is enough. A block editor is a frontend project, not a knowledge project. |
| **PDF export** | Low priority; use browser print-to-PDF in v1. |
| **Full customer portal redesign** | Out of scope; stay internal-only per constraints. |
| **Workspace-level sharing** (Odoo-style) | Over-engineered for single-team internal helpdesk. |

## Concrete First-Step Recommendation

**Start with K1: Better Search + Filters.**

### Why K1 first
1. **Fixes the most broken UX** — Today, agents can't find articles without guessing the exact title. Better search immediately reduces duplicate tickets.
2. **Lowest schema risk** — Zero new tables. Only query-parameter extensions to existing `/api/kb`.
3. **Highest reuse** — Ticket list already has the `q` + `category_id` + `status` filter pattern. Mirror it in KB.
4. **Fast feedback loop** — Can be built, tested, and shipped in 1–2 days without touching any other increment.
5. **Unblocks everything else** — Better search makes the links, collections, and analytics in K2–K5 actually discoverable.

### First-step checklist
1. In `routes_kb.py`, extend the `list_articles()` SQL builder to accept:
   - `status` filter
   - `author_id` filter
   - `date_from` / `date_to` (ISO strings, `created_at >= ?`)
   - `sort` (`updated_at`, `views`, `helpful_pct`)
2. Add a lightweight `helpful_pct` subquery: `(SUM(helpful) * 100.0 / COUNT(*))` from `kb_feedback`.
3. Frontend: add filter controls to Help Center list and Manage KB list. Show active filters as removable chips.
4. **Do not** add `parent_id`, `kb_article_links`, or `ticket_kb_links` yet.
5. **Do not** start the graph, analytics, or AI features yet.

Ship K1, validate with agents, then proceed to K2 (links).
