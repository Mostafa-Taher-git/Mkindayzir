# OpsDesk Dashboard Debate Brief

Context: OpsDesk is an internal company-only Flask + SQLite + vanilla SPA helpdesk. Current dashboard is minimal. The owner wants a professional Helpdesk Dashboard inspired by Odoo + Frappe, but not a clone.

## Mission
Debate the 4-phase dashboard plan below. Challenge assumptions, find gaps, rank risks, and return a revised plan with clear priorities. Do NOT edit code unless explicitly asked to implement; this run is for critique + revised plan only.

## Current State (Codebase-Grounded)
- `/api/dashboard` exists and returns: counts by status, unassigned, urgent, blocked, resolved, avg_resolution_hours (7-day rolling), aged tickets.
- Frontend `viewDashboard()` shows count tiles + aged tickets table. Title is "Manager Dashboard". Non-agents are redirected to `/my`.
- `/api/dashboard` already scopes to the agent's team when `user.role === "agent"` (via `team_id` filter). Managers/admins see global data.
- **Role detection is already implemented:** `/api/auth/me` returns `role` and `team_id`; frontend uses `state.user.role` everywhere (`isAgent()`, `isAdmin()`).
- Reports exist: `/api/reports/summary`, `/api/reports/workload`, `/api/reports/sla`, `/api/reports/trend`, `/api/reports/export.csv`. **All are manager/admin only and do NOT accept query filters** (no `?team_id=` or `?agent_id=` support).
- CSAT data exists: `tickets.csat` (1–5) is collected via `POST /api/tickets/<id>/rate`. `/api/reports/summary` already computes `avg_csat` and `csat_responses`.
- Teams are fully modeled: `teams` table, `users.team_id`, `tickets.team_id`.
- **Missing data-model concepts:** there is no "needs my reply" / "pending response" flag, no per-agent first-response-time aggregation, and no customer-feedback table separate from ticket CSAT.
- Tests: 73 passing. Thin Python, editable JS/CSS frontend.

# CRITIQUE & REVISED PLAN

## Summary of Critique

**The plan is too big for a first iteration.** Five new API endpoints + full role-based frontend + global filters + charts is 6–8 weeks of work. The dependency chain (Phase A → B → C → D) creates a long feedback loop with no user-visible value until Phase B completes.

**Critical gaps found in codebase inspection:**
- **Reports are not filterable today.** `/api/reports/*` does not accept `team_id`, `agent_id`, or `period` params. Reusing them for manager/agent-specific views requires adding query-param support first — this is non-trivial because each report has its own SQL.
- **No "needs reply" data model.** There is no `pending_reply`, `last_read_at`, or `awaiting_agent_response` concept. "Needs My Response" cannot be built without either a schema change or a heuristic (e.g., tickets assigned to me with no internal note from me in the last N hours).
- **No first-response-time aggregation.** `ticket_sla.first_response_at` exists per ticket, but no endpoint averages it. `/api/reports/summary` does not include it.
- **Global filter bar is a UX rabbit hole** — state sync across role-different widgets, URL persistence, back-button behavior.
- **The "0 new endpoints" shortcut is wrong.** The existing plan assumes reports can be filtered; they can't without backend changes.

**Wrong phase order:** API expansion first delays all user value. Frontend-first with branched existing logic validates UX in hours, not weeks.

## Ranked Risks (High → Low)

1. **Scope creep / never shipping** — 4 phases with hard dependencies = high abandonment risk
2. **Missing action-queue data model** — "Needs My Response" / "Pending Reply" has no source of truth; building it requires schema migration or fragile heuristics
3. **Global filter complexity** — synchronized state across role-different widgets is hard to get right
4. **Reports are not reusable as-is** — 4 existing report endpoints lack `team_id`/`agent_id`/`period` filters; treating them as shortcuts overstates their current value
5. **Over-engineering APIs** — 5 new endpoints when 2–3 could suffice
6. **Chart library decision deferred** — Phase D assumes charts; no evaluation of Chart.js vs ApexCharts vs native SVG
7. **Team cards scope** — `/api/dashboard/teams` assumes a team-centric UX; verify managers want clickable cards vs simple tables

## Revised Plan: 3 Increments

### Increment 1: "Fix the Agent Dashboard" (1–2 days)
**Goal:** The largest user group (agents) currently sees a manager-branded dashboard with team-wide aggregates. Ship role-aware dashboards by branching existing code, not building new endpoints.

**Backend (0 new endpoints — modify existing):**
- `GET /api/dashboard` — add role branch:
  - If agent: return `my_open`, `my_assigned`, `my_blocked`, `my_urgent`, `my_resolved_today`, `my_avg_response_hours`, `my_avg_resolution_hours`, `my_rated_tickets`, `needs_attention` (aged tickets assigned to me).
  - If manager/admin: keep current global/team-scoped shape (already works).
- Reuse `/api/reports/trend?days=30` for the trend widget (no changes needed; manager-only restriction is acceptable for Increment 1).

**Frontend:**
- Modify `viewDashboard()` to branch on `state.user.role`:
  - Agent view: "My Dashboard" heading, 5–6 KPI tiles, "Needs Attention" list (click → ticket).
  - Manager view: keep existing "Manager Dashboard" layout.
- Remove the `if (!isAgent()) { navigate("/my"); return; }` redirect for agents; agents stay on dashboard.
- Loading skeletons, empty states, error toast.

**Tests:** 3 endpoint tests (agent shape, manager shape, requester forbidden) + 2 frontend rendering tests.

**Why this wins:** Agents get real value in 1–2 days. No new endpoints, no new schemas, no global filters. It is a refactor of what already exists.

---

### Increment 2: "Manager Action Center" (Week 2–3)
**Goal:** Give managers team visibility and an action queue. Accept that reports need filter support first.

**Backend (add filter params to reports + 1 new endpoint):**
- Add optional `team_id` and `agent_id` filters to:
  - `/api/reports/summary?team_id=X`
  - `/api/reports/workload?team_id=X&agent_id=Y`
  - `/api/reports/sla?team_id=X`
- Add `GET /api/dashboard/action-center` — manager-scoped: unassigned tickets, SLA breaches (from `ticket_sla.breached=1` or `breach_at < now`), pending reply heuristic (open tickets assigned to a team with no agent comment in last 4h). **This is the only truly new endpoint.**
- **Defer `/api/dashboard/teams` to Increment 3** — team cards are polish, not core value.

**Frontend:**
- `viewDashboard()` for manager/admin: KPI strip (from `/api/reports/summary?team_id=`), Action Center section (from `/api/dashboard/action-center`), Team Workload mini-table (from `/api/reports/workload?team_id=`).
- Drill-down: each KPI links to `/queue` with pre-filled filters (`?team_id=X&status=open`, etc.).
- No global filter bar yet — fixed to current user's team (or all teams for admin).

**Tests:** Filter integration tests + action-center endpoint tests + manager view rendering.

---

### Increment 3: "Polish & Extend" (Week 4–5)
**Goal:** Charts, global filters, agent-specific reports, admin view.

**Backend:**
- Add `period` param to `/api/dashboard` (simple: `?period=7d|30d|90d`).
- Add `GET /api/dashboard/my` — agent-scoped deep link (first response time, resolution time by category, my CSAT distribution). **Only if Increment 1–2 show agents hitting the dashboard multiple times per day.**
- Add `GET /api/dashboard/csat` — ticket CSAT distribution + recent ratings. **Only if `tickets.csat` has > 50 non-null rows in production data.**

**Frontend:**
- Global filter bar (period, team) — **only on manager/admin views**.
- Charts: Chart.js (lightweight, tree-shakeable) for FRT/Resolution trends + SLA gauge.
- Admin view: system health (DB size via `data/` dir, active users today, error count from logs).
- Refresh button, keyboard shortcuts, URL state persistence.

**Tests:** Chart rendering, filter persistence, E2E happy paths.

## Quick Win: Reuse Reports vs New Endpoints

| Need | Proposed New Endpoint | Actual Reuse Strategy | Notes |
|------|----------------------|----------------------|-------|
| Agent KPIs | `/api/dashboard/my` | **Modify `/api/dashboard`** — add agent branch | 0 new endpoints; refactor existing |
| Manager KPI strip | `/api/dashboard` + filters | `/api/reports/summary?team_id=X` | Must add `team_id` filter to reports first |
| Team trends | `/api/dashboard/teams` | `/api/reports/workload?team_id=X` | Must add `team_id` filter to reports first |
| SLA compliance | `/api/dashboard/action-center` | `/api/reports/sla?team_id=X` | Must add `team_id` filter to reports first |
| Unassigned / SLA breaches / pending reply | `/api/dashboard/action-center` | **New endpoint** | No existing source for "pending reply" |
| CSAT distribution | `/api/dashboard/csat` | `/api/reports/summary` (has `avg_csat`) | Only distribution/trend is missing |

**Verdict:** Only **1 new endpoint** is truly needed: `/api/dashboard/action-center`. The rest can be solved by:
1. Adding `team_id` / `agent_id` / `period` query params to the 4 report endpoints, and
2. Branching `/api/dashboard` on role instead of creating `/api/dashboard/my`.

Delete the other 4 proposed endpoints from Phase A.
